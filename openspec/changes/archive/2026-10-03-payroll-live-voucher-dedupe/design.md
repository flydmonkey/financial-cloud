## Context

见 proposal.md 的原因。两个 Mapper 注解查询目前按创建时间取一个裸关联，再由服务检查凭证是否存在；当前行自身关联非空时还会跳过历史查询。第一轮已保护顺序修改/删除和凭证删除原子性，未解决该查重漏洞。当前数据库与凭证逻辑删除约定为 `deleted='n'` 表示有效。

## Goals / Non-Goals

**Goals:** 保证失效引用无法遮蔽同业务范围的有效凭证；拒绝路径无清理和保存。查询有效性由实际 SQL 多行夹具验证，服务控制流单独验证。

**Non-Goals:** 不增加锁、CAS、业务唯一键，不批量修历史链接，不修改 0/2 计提和 1/3 发放分流及模板口径，不调整其他修改/删除接口。

## Decisions

- 两个查询改名为 `findAnyLiveAccrualVoucherId` / `findAnyLiveSalaryVoucherId`，关联 `voucher` 并在 `LIMIT 1` 前筛选 `v.deleted='n'`。相对返回所有关联逐个查凭证，该方案保持小范围修改且不增加 N+1 查询。
- 保留当前行 own live 快速拒绝；own 为空或失效时始终查 live peer。命中直接拒绝；未命中时只清理 own stale，随后走现有生成逻辑。
- 工资查询仍包含历史软删行；不增加凭证状态、日期或凭证 book 过滤，以保持原按关联 ID 判有效及查重范围。原工资侧 book/employee/month 和关联列范围不变。
- Java mock 服务测试检验拒绝/放行和写入边界；Python 测试直接提取真实注解 SQL，在指定 `financial_cloud_e2e*` 库同会话的临时表执行，不复制 SQL，不清除真实账套。保留旧 Mapper 字节用于相同夹具的反证。该方式检验 MySQL 查询语义，不能替代 MyBatis 参数绑定或完整业务 E2E。

## Risks / Trade-offs

- [并发读写仍可能重复生成或覆盖链接] → 单列后续 R0 风险，不以本切片通过宣称全部薪资并发安全。
- [现场历史状态未知] → 固定夹具仅证明条件性漏洞和修复；不据此声称生产已发生金额事故。
- [临时表权限或隔离库不可用] → 保留失败原因，不能用 mock 查询结果代替实际 SQL 验证。

## Migration Plan

无需 schema 或数据迁移。交付经审查和验证的源码；需要回滚时恢复本切片服务/Mapper 版本即可，原历史记录不被批量改写。正式部署依照候选发布证据门槛与授权执行。
