## Context

动机见 [proposal.md](proposal.md)。`tools/run_accounting_acceptance.py` 已有隔离库限制、9 组顺序验收、每次唯一报告目录及 `--retries=0`。它目前只记录传入库名、URL、汇总统计和人工签字 pending；若缺少失败统计字段，会默认零，且不能校验完整场景或实际运行产物。账套隔离有单独套件，不能仅从会计验收摘要推定其通过。

CI 的 PR 冒烟与 push 完整验收范围不同，当前运行 Vite；生产前端产物与完整运行身份不能从现有绿色记录中推导。首轮历史证据绑定 `9758a9a` 上未提交工作区，当前提交 `4571047` 已归档首轮变更。系统没有已验证可直接提供提交、JAR 哈希及实际数据源绑定的运行身份接口。

## Goals / Non-Goals

**Goals:**

- 以版本化文件协议和现有 Python 工具实现离线核验，让开发与会计复核人员可以看懂每个未满足条件及下一步。
- 核验器与有写入能力的验收运行器分开；fixture 测试可以不启动任何业务服务完成。
- 在证据不足时仍产出完整阻塞清单，不因首个缺项停止分析。

**Non-Goals:**

- 本轮不更改记账流程，不建设 CI 调度平台、运行身份 API、电子签章或发布系统。
- 不在核验命令中触发完整测试、恢复、清库、网络取证或远端 CI；人工与环境依赖按输入证据核验。
- 不将证据校验等同于财务合规认证或正式部署许可。

## Decisions

### 1. 一个证据包，分别保存候选、原始事实与评估结果

采用 UTF-8 JSON v1，顶层为 `schemaVersion`、`candidate`、`profile` 和 `evidence`。新增 `tools/verify_release_evidence.py` 只消费该协议。候选与证据条目至少记录：

| 对象 | 必需信息 |
|---|---|
| candidate | candidateId、40 位 commitSha、源码状态/指纹、backend SHA-256、生产 frontend 清单及 SHA-256 |
| profile | 受版本管理的发布验收 profile ID、版本、哈希；固定必需检查集合 |
| acceptance | runId、开始/完成时间、候选与产物身份、各组原始报告路径/哈希、执行范围 |
| environment | 实例与数据源身份、API/前端地址、运行绑定证据路径/哈希、采集方法、技术复核人及结论 |
| ci | 提供者、runId/URL、headSha、所运行 workflow、必需 job/step 结论、原始导出/产物引用与哈希、来源复核记录 |
| accountant | 真实完整月份、参与角色、核对表与各方签字文件引用/哈希、对应候选及结果 |
| issueReview | 对应候选、现有问题台账引用/哈希、复核人/时间、金额差异说明及会计认可、各发布阻塞项状态、非阻塞项责任人与计划 |
| restore | 来源/独立目标实例与数据源身份、候选产物、备份包哈希、业务数据/附件/账簿/三表核对证据、复核结论 |

后端哈希对应实际 JAR；前端哈希由排序后的相对文件名、大小和内容 SHA-256 清单生成，不使用打包时间作为身份。源码记录完整 SHA、Git tracked/untracked 状态及排序文件清单；脏源码或采集前后状态变化均阻塞发布就绪，执行测试本身仍可作为研发验证。

不采用只存总测试数和 `passed` 的简表，因为无法定位遗漏与来源。不同运行可以组成同一候选证据包，但每项候选、源码及产物身份必须一致；不要求所有外部证据同时采集。

### 2. 由受版本管理的验收 profile 定义完整范围

新增 `tools/release_evidence_profile.json`，保留现有 9 组名称和 spec 归属，单列 `book-isolation.spec.ts`，并记录测试项目及稳定 case 身份。实施时从当前候选的 Playwright 测试清单取得初始集合，人工审查后纳入版本管理；后续测试变更须同步审查 profile。证据包不能自行删减必需集合，核验时比对可信本地 profile 及其哈希。

原始 Playwright JSON 须包含 `stats` 的 expected/unexpected/skipped/flaky、errors 和具体 test/results；核验实际 case 身份、首个尝试成功、无重试、无跳过、无失败及执行完成，不从缺失字段推导零。禁止重复条目拼数量。组退出码与原报告须一致。历史“50/25 项”仅说明当时范围，不硬编码成未来唯一合格数量。

实际 CI 要求该候选完整 SHA 下后端与前端检查以及完整 E2E/会计验收等必需范围都有实际成功结论。PR 冒烟不能替代完整范围，job/step 缺失或 skipped 视为不足。生产前端身份、是否确实以该产物执行验收单独核验；当前 Vite 测试证据不能自动证明生产前端产物验收。

### 3. 采集来源与确认运行绑定是不同证据

现有运行器在测试启动前记录源码、可获取的构建产物和声明环境信息，完成时记录最终源码状态、报告哈希与失败信息。未知字段显式标记 unknown；没有发布绑定资料时仍能执行原有隔离验收，但摘要不得宣称发布就绪。

`FC_DB_NAME`、`E2E_API_URL` 和本地 JAR 哈希均记为 declared。运行绑定须提供技术复核过的执行记录，证明启动/部署的实际后端与前端产物及其数据源；记录采集方法、实例身份、对应运行和支持材料哈希。当前无运行身份接口，本轮接受技术人员实际观察并复核的部署/启动与数据源记录，不用声明值自动补齐。缺少或无法对应仍阻塞。

CI 和人工证据采取同样原则：离线核验结构、身份、完整性及复核记录，外部来源真实性由指定复核人员根据原 CI run、签字及恢复记录确认。工具不能独立认证人为伪造的一整套文件；结果明确这一信任边界。无需在本轮扩大为后端接口或在线认证服务。

### 4. 所有缺项同时输出，结果保守且可操作

每个 condition 使用 `satisfied`、`missing`、`failed`、`identity_mismatch`、`insufficient_scope` 或 `pending_review`，并带 `evidenceRef`、`reason`、`nextAction`。只在全部必需条件 satisfied 时 `releaseReady=true`。JSON 和 Markdown 来自同一评估结果，稳定排序，只有明确提供 `--json-output`/`--markdown-output` 时导出文件；导出不得覆盖输入证据。

命令建议为 `python tools/verify_release_evidence.py --bundle <root>/candidate.json`，退出码 0 表示证据就绪，1 表示可解析但仍被阻塞，2 表示输入/格式错误。可解析的局部缺项必须逐项报告。输出只包含定位和核验所需信息，不展开会计原始数据、签名内容或连接凭据。

证据引用使用 bundle root 下相对路径。读取前 resolve 并验证范围，拒绝绝对路径、目录穿越和符号链接逃逸。核验模块不调用 subprocess、网络、数据库或验收运行器；报告输出只写显式目的地，不修改候选或原始报告。

### 5. 人工试账与独立恢复保持各自范围

会计签字沿用 `docs/testing/accountant-month-pilot.md` 的真实完整月份核对和会计/业务操作/技术角色。pending 或只填测试月份、没有实际核对与签字附件的资料不能通过。

恢复记录须证明独立目标后端实例与数据源、备份包身份和业务核对结果；同实例清账套后恢复保留为同实例证据。数据/附件、账簿及资产负债表、利润表、现金流表均需结论。未提供第二实例时可完成工具实现和 fixture 验证，产品发布条件继续待环境。

复用试账文档的问题记录作为 `issueReview`，不建立新台账系统。即使其余条件均通过，仍须核验金额差异已解释并经会计认可，金额错误、跨账套访问、恢复丢失和无法结账等发布阻塞问题均已修复复核。缺少台账复核或存在未关闭阻塞项时继续阻塞；非阻塞流程/文案问题保留责任人与处理计划。

## Risks / Trade-offs

- [历史证据来源不完整] → 保留原样并列阻塞，不给旧结果补写当前 SHA；后续在明确候选和隔离环境重新采集。
- [纯离线工具无法认证伪造的外部资料] → 显示来源与技术/会计复核记录，保留信任边界，不输出“独立认证”结论。
- [profile 与测试发生漂移] → profile 哈希和具体 case 核验；修改测试时审查更新 profile，不以汇总数量放宽范围。
- [当前验收运行 Vite、无运行身份接口] → 明确产物或绑定范围不足，工具如实阻塞；运行身份 API 与 CI 生产前端改造可另行立项。
- [同一工作区有其他未提交资料] → 采集完整源码状态；发布验收采用干净候选工作区，工具不删除用户文件来达成“干净”。

## Migration Plan

1. 在工具与文档中引入 v1 协议、可信 profile 和只读核验入口，不迁移业务数据库。
2. 增强运行器记录来源，不改变隔离限制、逐组执行和人工签字 pending 的原有事实。
3. 旧报告保持可阅读；发布核验遇到缺少 v1 身份资料时说明阻塞原因，不自动升级成当前候选证据。
4. 用完整合成 fixture 验证成功路径，用当前保留资料验证阻塞清单；合成通过记录明确标注为测试 fixture，不能成为真实发布证据。
5. 工具与文档可独立撤回，无数据迁移；不会自动触发发布。实际 CI、真实月试账和第二实例恢复须后续实际执行并复核。
