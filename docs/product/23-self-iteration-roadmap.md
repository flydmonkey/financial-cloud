# 23 · 产品迭代路径与自我迭代机制

> 建立日期：2026-10-02。默认服务小微企业会计和代账会计，优先保证账务结果可信、月结顺畅、交付可恢复。本轮已进入自主迭代，首片工资明细与凭证关联完整性已实现并通过本地验证，见 [第 1 轮记录](../testing/self-iteration-01-2026-10-02.md)；尚未正式发布。

## 1. 从现有能力出发

产品已具备建账、期初、凭证、账簿、结转、结账、三表和月度账本包主闭环，并具备往来核销、资产、日记账、工资最小闭环、报销、打印/PDF、多账套工作台、角色及账套隔离、手动/定时备份和含附件的 v2 恢复。详见 [产品总览](00-overview.md)、[差距清单](20-gap-analysis.md) 和 [上一版路线](21-roadmap.md)。这些能力作为迭代底座，不重复立项。

研发程序收口、自动验证通过、真实会计认可和生产发布是不同状态。当前基线是提交 `9758a9a`，上一轮实现提交为 `4432d26`、`20d40ec`。其 [收尾记录](../testing/2026-10-02-round-closeout.md) 报告后端 487 项、会计验收 50 项、账套隔离 25 项、前端单测 34 项、工具安全单测 5 项通过，并记录构建、类型检查及 27 项主规格严格校验通过。

上述数字是**上一轮历史证据，不代表本轮新增改动已通过测试**。本轮必须记录实际命令、候选提交或工作区状态、环境、结果与证据路径；未运行的检查保持待验证。

当前未完成：实际远端 CI、真实完整月份平行试账与负责人员签字、真实第二实例恢复演练和正式发布。现有 v2 恢复证据来自同一隔离实例删除源文件并清空源账套业务后的恢复，不能改写为真实第二服务器验收。依据见 [会计验收](../testing/accounting-acceptance.md)、[平行试账](../testing/accountant-month-pilot.md) 和 [便携备份边界](../testing/portable-book-backup.md)。

沿用已有产品边界：单账套内结账和过账；多账套工作台承接进度一览、进入处理、已结账本包导出。跨账套批量结账/过账、结账就绪聚合编排不进入本路线。税局直连、移动端、员工自助和正式 SaaS 计费保持储备。R4 是后续候选研究，不能据此自动启动历史明确排除的功能。

## 2. 五阶段路线

按退出标准推进，不以固定日期或功能数量宣称完成。阶段顺序是 R0 → R1 → R2 → R3 → R4；真实资料或环境等待期间，可继续后续阶段的只读研究、基线测量和小范围设计，不能绕过前置验收扩大上线范围。

### R0 · 账务可靠与发布准备

**用户问题**：工资、凭证与账簿必须保持一致；会计和管理员需要知道当前候选版本是否有足够证据投入试用或发布。

**进入条件**：已有主闭环和独立验收底座；优先处理已确认、可复现的金额、关联、隔离、恢复或月结问题。

**可交付切片**：

1. 首片 `payroll-voucher-link-integrity`：工资已有计提或发放凭证关联时保护普通修改和删除；整批删除先校验；工资凭证删除失败保留关联，成功删除与解除关联保持事务一致；重复生成继续被拒绝。当前切片以该 OpenSpec 变更为准，既有底座见 [工资主规格](../../openspec/specs/payroll-smb/spec.md)。
2. 发布候选证据核验：绑定版本与环境，区分本地测试、实际 CI、会计签字和目标恢复；生成待办及阻塞清单，拒绝用旧版本证据或空白签字表判定可发布。
3. 正常推送后检查实际 CI，修复真实失败；核对必要升级项、v1/v2 备份兼容和回滚条件，形成可审阅的发布方案。
4. 用经授权的真实完整月份完成平行试账；在指定第二测试实例完成备份恢复演练。条件不足时保留人工待办，不模拟签字。
5. 逐项核验会计软件规范与当前实现的对应关系，记录适用性、证据和差距；确认的高风险缺口进入 R0，而非等待远期扩容。

**退出标准**：本轮风险修复经独立审查及必要验证；候选提交的实际 CI 成功；无未解决的金额、跨账套访问、恢复丢失、无法结账等发布阻塞项；真实月份差异经会计认可并签字；目标恢复证据完整；发布与回滚方案可审阅。正式部署仍需明确目标和发布授权。

**指标**：已复现工资场景的关联与账簿变化、重复凭证生成数、未解决发布阻塞数、候选版本证据完整度、恢复账表/附件差异。质量门槛为失败操作后关联/凭证/余额不变，成功操作符合预期；发布阻塞为 0。覆盖率只描述实际场景，不宣称所有接口已穷尽。

**投入与依赖**：单个明确修复通常按小切片估算，约 1–3 个有效开发日；证据核验及发布准备约 2–5 个有效开发日。实际范围经规格后调整。会计试账、远端 CI 和第二实例恢复的等待时间单列，不计入代码估算。

### R1 · 真实试用闭环

**用户问题**：功能可用仍可能需要反复找入口、解释差额或依赖开发人员绕行；真实会计需要稳定完成连续日常工作。

**进入条件**：R0 修复候选版可用于隔离试用，负责人、资料授权与试用账套明确。访谈和问题模板可提前准备。

**可交付切片**：按 [平行试账清单](../testing/accountant-month-pilot.md) 记录真实步骤和差异；形成问题台账；对高频入口、阻塞原因、导入反馈和更正路径做小范围修复。已有首页指引、月结处理建议、闭期交付入口继续复用，不重新建设。

**退出标准**：操作人员可独立完成建账接手、日常处理、月结、更正及交付；试用问题有复现、责任、处理结论和会计复核；金额差异无未解释项；进入后续阶段时有可比较的真实使用基线。

**指标**：首次独立月结完成情况、每个账期开发人员介入次数、绕行步骤数、问题重现/解决/复核比例、关键任务实际耗时。先记录任务口径与样本量，再设改进目标，不承诺未经测量的提升百分比。

**投入与依赖**：每次试用反馈安排 1–2 个明确问题切片；通常每片约 1–3 个有效开发日。试用观察随真实账期进行，负责人和资料未到位时继续处理可复现缺陷及测量工具。

### R2 · 代账吞吐

**用户问题**：代账会计在接手数据、反复录入、更正和交付中耗时，多个客户会放大每次重复操作。

**进入条件**：R1 有真实任务耗时和问题频次；账务可靠性、权限和单账套结账边界保持稳定。

**可交付切片**：根据实测瓶颈选择接手导入的错误定位、同一账套内的录入/更正提速、常用模板和检索细节、现有工作台进入处理及已结交付的摩擦修复；评估真实规模下的查询、导出和备份资源边界。期初 Excel、凭证工作台、多账套工作台和批量已结账本包均已存在。

**退出标准**：选定任务在相同业务规模与正确性口径下优于基线；错误反馈可定位到待处理项；提速路径保持金额、权限、审计和可逆更正；较大规模的边界有实测与失败处理说明。

**指标**：每套接手耗时、每百张凭证实际处理时间、导入失败定位耗时、更正往返次数、交付耗时、指定规模的 P95 响应和内存峰值。使用固定样本或同类真实样本比较，目标在首轮测量后确定。

**投入与依赖**：每轮仅选择一个主要瓶颈，粗估 3–10 个有效开发日；缺少代表性样本时不将猜测升级为承诺。没有跨套结账或跨套批量过账切片。

### R3 · 小微经营

**用户问题**：老板已有经营看板，但需要理解数字所属期间、来源和变化，才能与会计讨论资金、利润和往来。

**进入条件**：账表验收稳定，客户真实关心的问题已收集；相关口径由负责会计确认。

**可交付切片**：围绕现有首页看板改进口径解释、期间一致性、业务溯源和异常原因；按真实需求试点资金与逾期往来行动提示、月度交付解读。现有老板视图、税费测算、税负预警、账龄与下钻继续复用；不另建重复的老板报表页。

**退出标准**：关键指标可追溯到对应账期与账务证据，能解释与会计报表的差异；老板与会计可共同理解提示；新增提示具有明确处理入口和有效性复核。预测类能力必须先明确数据条件、口径及适用边界。

**指标**：指标解释成功情况、来源定位耗时、重复咨询次数、提示被采纳/处理比例和误报比例。先做小样本验证，按用户反馈确定是否产品化。

**投入与依赖**：一类经营问题约 3–10 个有效开发日，包括口径核对与试用；不能仅凭现有卡片数量判断经营价值。

### R4 · 智能辅助与生态

**用户问题**：在成熟账务流程中减少票据转录和外部数据搬运，并保持原始证据与人工审核能力。

**进入条件**：R0–R3 有稳定用户价值；代表性电子凭证/票据样本、资料授权和成本预算明确；重新确认候选范围。

**可交付切片**：先研究电子凭证结构化标准适配与原件保留、去重、校验、业务溯源，再按样本选择解析或识别辅助；经确认后探索科目/摘要建议和受控导入接口。AI 输出默认作为人工核对的草稿或建议，不能直接替代审核、过账、结账或签字。税局/银行直连、移动端及 SaaS 计费需另行立项。

**退出标准**：选定样本范围的处理结果可核验、可追溯、可更正；失败有回退流程；错误及成本可测；人工确认不会被跳过；标准适配已完成具体条目的证据核对，不能用“能识别附件”替代全流程验证。

**指标**：按凭证类型统计字段准确率、人工修正比例、重复识别情况、每份资料的处理成本及耗时、原件与结构化数据关联完整度。代表性样本基线完成后再设门槛，不预设准确率。

**投入与依赖**：先做约 3–5 个有效开发日的样本和接口研究，形成成本与风险结论；是否进入开发及开发估算在研究后决定。此阶段暂不自动启动。

## 4. 自我迭代循环

1. **发现**：从真实操作、代码审计、测试失败及交付恢复中识别问题；保留触发条件、预期/实际、影响与证据，先查已有功能和归档，排除重复需求。
2. **排序**：先修金额、关联、权限、恢复和月结风险；再选高频且已测量的主流程摩擦；只取一个能独立验收的切片。
3. **规格**：使用项目 OpenSpec，定义范围、非目标、失败行为、验收场景、数据和回滚影响；新增能力前核对本路线与既有边界。
4. **实现**：沿用现有服务、界面和验收工具；保护成功路径与拒绝后的数据不变。隔离验证只使用明确指定的测试环境和测试库。
5. **独立审查**：由独立审查者检查业务不变量、角色/归属、事务、边界与必要用例；问题修复后再进入验证。
6. **必要验证**：按影响范围运行服务/前端检查及相关隔离场景；涉及共享账务或发布候选时运行相应完整回归。记录本轮真实结果，不以发现测试数量、重试成功或历史日志冒充完成。
7. **更新状态**：同步规格、任务、产品现状和验证记录，按项目流程同步与归档；明确已完成、待人工输入和发布阻塞，再选择下一切片。失败先查原因，不能降低断言来获得通过。

本机制用于当前会话内自主推进，不建立定时任务，不对外发送消息。需要真实会计、目标环境或发布授权时，一次列出具体缺口，并继续不依赖这些输入的代码、规格、测量与文档工作；不会代签、补造结果或自行操作真实账务。
