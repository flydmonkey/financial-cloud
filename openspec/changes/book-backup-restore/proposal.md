# Proposal: 账套备份与恢复（book-backup-restore）

## Why

代账合规的最后一块 P0 短板：系统目前**没有任何数据备份能力**。账套数据（凭证链、科目、资产、薪资、日记账）只存在一份 MySQL 里，一旦误删账套、误操作反结账链、或实例损坏，代账公司无法向客户交代。差距清单（docs/product/20-gap-analysis.md §1.5 / §8.3）与路线图 S3 均将其列为 P0。账本包 ZIP 解决的是"给客户看的报表交付"，备份解决的是"给系统恢复的数据保全"，两者不合并。

## What Changes

- 新增**账套级手动备份导出**：按当前账套一键导出业务备份包 ZIP（`manifest.json` + 每表 JSONL 数据），覆盖凭证链、科目与期初、辅助核算、日记账、固定资产、薪资、结账、报表数据、账套配置共 30+ 张账套级表。
- 新增**备份恢复**：上传备份包，校验 manifest（格式版本、账套元信息、行数与校验和），**恢复为一个新账套**（克隆式恢复，不覆盖现有账套），所有主键与外键按声明式映射表重映射到新 ID。
- 入口落在账套管理页：每行「导出备份」+ 列表上方「恢复备份」。
- 权限与账套授权沿用现有 `permission_book` 体系；导出/恢复均记操作审计（history_event）。

## 形态决策（拍板项，对应 roadmap §5 待决问题）

选 **B. 账套级业务包**，理由：

- 代账场景的天然单位是账套（一个客户一套账），库级 dump 会带走其他客户数据，违背数据隔离；
- 账套级包可跨实例迁移（交付给客户的自持备份、换服务器），库级 dump 不能；
- 与账本包（报表交付）职责清晰分离。

**恢复策略：仅支持恢复到新账套**（v1 不做覆盖式恢复）。覆盖恢复需要删除目标账套全部凭证链，属于高危操作；克隆式恢复纯增量、可比对、可删除，恢复演练零风险。

## Non-goals（写死）

- 不做定时/自动备份（v2，需调度与存储策略）
- 不做覆盖式恢复、不做跨账套合并
- 不备份用户/权限/日志/会话等实例级数据（恢复目标环境的用户体系独立）
- 不做备份包加密与口令保护（v2）
- 不做库级 dump 集成（mysqldump 依赖运维侧，属部署文档范畴）

## Capabilities

### New Capabilities

- `book-backup`：账套业务备份包的导出（范围、格式、清单校验）与克隆式恢复（校验、ID 重映射、事务语义）。

### Modified Capabilities

- （无：不改既有能力语义。）

## Impact

- **后端**：新增 `service/book/BookBackupService`（导出组装 + manifest 校验）与 `BookRestoreService`（解析 + ID 重映射 + 事务恢复）；新增 `controller/book/BookBackupController`（`POST /api/book/backup/export`、`POST /api/book/backup/restore`）。声明式表规格清单（表名 + 过滤列 + FK 边）是核心设计物。
- **前端**：账套列表页加导出入口与恢复上传对话框（`views/books/index.vue`）。
- **依赖**：复用现有 ZIP/下载与 `ExcelExporter` 无关；恢复用现有 `BookService.save` 的账套初始化能力建壳后灌数据。
- **测试**：备份包完整性（表齐全、行数一致）、往返一致性（导出→恢复到新账套→关键金额与凭证数比对）、校验失败路径（篡改 manifest/缺表/版本不符）、权限拒绝。
- **风险**：ID 重映射遗漏某条 FK 边会产生脏数据 → 设计物中枚举全部 FK 边并配单测覆盖每条边。
